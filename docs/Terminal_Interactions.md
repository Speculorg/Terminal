
# Взаимодействия в Speculorg.Terminal

В этом документе перечислены способы взаимодействия Компонентов и процессов в Speculorg.Terminal.

## Введение

Система Speculorg.Terminal поддерживает три ключевых способа взаимодействия для обмена данными между компонентами и внешними сервисами:

- **Синхронное взаимодействие (REST API):** Используется для операций с быстрым откликом и прямыми запросами.

- **Асинхронное взаимодействие (RabbitMQ):** Применяется для передачи событий и данных между микросервисами.

- **Потоковое взаимодействие (WebSockets):** Обеспечивает обновления в реальном времени для клиентов.

## REST API

- **Описание:**
    - Синхронное взаимодействие в системе Speculorg.Terminal осуществляется посредством REST API, предоставляя клиентам и микросервисам возможность обмениваться данными в режиме реального времени.
    REST API использует протокол HTTP и поддерживает стандартные методы (GET, POST, PUT, DELETE), обеспечивая простоту интеграции и широкую совместимость.

- **Основные аспекты:**
    - API Gateway: Центральная точка входа для всех внешних запросов к системе. Обеспечивает маршрутизацию запросов к соответствующим микросервисам, а также функции аутентификации, авторизации и логирования.
    - Контроллеры: Каждый микросервис содержит контроллеры, обрабатывающие входящие HTTP-запросы и вызывающие соответствующие методы бизнес-логики.
    - Формат данных: Обмен данными осуществляется в формате JSON.
    - Версии API: Для обеспечения обратной совместимости и плавного обновления системы используется версионирование API (например, `/api/v1/...`).

- **Безопасность и контроль доступа:**
    - Аутентификация: Все запросы к защищённым ресурсам требуют наличия JWT-токена в заголовке `Authorization`.
    - Авторизация: Проверка прав доступа на основе ролей пользователя и разрешений, определённых в `Speculorg.Terminal.Security`.

- **Ошибки и обработка исключений:**
    - Стандартные коды ошибок: Используются коды состояния HTTP (например, 400 Bad Request, 401 Unauthorized).
    - Сообщения об ошибках: Возвращаются в формате JSON с описанием ошибки и, при наличии, дополнительной информацией.

- **Примеры взаимодействия:**
    - Получение рыночных данных:
        - Запрос: `GET /api/v1/market/tickers/BTCUSD`
        - Описание: Клиент запрашивает текущую котировку для пары BTC/USD.
        - Обработка: API Gateway перенаправляет запрос к микросервису `Speculorg.Terminal.Market.Service`, который возвращает актуальные данные.
    - Размещение торгового ордера:
        - Запрос: `POST /api/v1/trading/orders`
        - Описание: Клиент запрашивает создание нового ордера.
        - Тело запроса: Данные о типе ордера, активе, количестве и цене.
        - Обработка: API Gateway перенаправляет запрос к микросервису `Speculorg.Terminal.Trading.Service`, где проходит валидацию и создаётся новый ордер.
    - Управление портфелем:
        - Запрос: `PUT /api/v1/assets/portfolio`
        - Описание: Обновление состава портфеля пользователя.
        - Обработка: API Gateway перенаправляет запрос к микросервису `Speculorg.Terminal.Assets.Service`, который обрабатывает запрос и сохраняет изменения.

## RabbitMQ

- **Описание:**
    - Асинхронное взаимодействие между компонентами системы Speculorg.Terminal реализуется с использованием брокера сообщений RabbitMQ. Это позволяет микросервисам обмениваться данными и событиями без непосредственного синхронного вызова, повышая отказоустойчивость и масштабируемость системы.

- **Основные аспекты:**
    - Очереди сообщений: Используются для передачи сообщений между микросервисами. Каждая очередь может быть привязана к определённому типу сообщений или событий.
    - Публикация и подписка: Микросервисы могут публиковать сообщения в очереди и подписываться на них для получения информации о событиях.
    - Формат сообщений: Сообщения передаются в формате JSON.

- **Преимущества:**
    - Масштабируемость: Возможность добавлять новые обработчики сообщений без изменения существующих сервисов.
    - Отказоустойчивость: Если сервис-получатель временно недоступен, сообщения остаются в очереди до восстановления.
    - Снижение нагрузки: Разгрузка сервисов за счёт асинхронной обработки задач.

- **Обработка ошибок и подтверждение сообщений:**
    - Подтверждение сообщений: После успешной обработки сообщения сервис отправляет подтверждение, что позволяет RabbitMQ удалить сообщение из очереди.
    - Повторная попытка обработки: В случае ошибки сообщение может быть возвращено в очередь для повторной обработки или перенаправлено в очередь ошибок.

- **Примеры взаимодействия:**
    - **Обновление рыночных данных:**
        - Микросервис `Speculorg.Terminal.Integration.Service` получает новые данные от микросервиса адаптера биржи.
        - Публикует сообщение в очередь `market_data_update`.
        - Микросервис `Speculorg.Terminal.Market.Service` подписан на эту очередь и обновляет свои данные при получении сообщения.
    - **Исполнение ордера:**
        - После размещения ордера микросервис `Speculorg.Terminal.Trading.Service` публикует сообщение в очередь `order_placed`.
        - Микросервис `Speculorg.Terminal.RiskManagement.Service` получает сообщение и анализирует риски, связанные с новым ордером.
    - **Уведомления пользователям:**
        - При наступлении определённого события (например, достижение цены актива) микросервис `Speculorg.Terminal.Analytics.Service` публикует сообщение в очередь `user_notifications`.
        - Микросервис `Speculorg.Terminal.Notifications.Service` обрабатывает сообщение и отправляет уведомление пользователю.

## WebSockets

- **Описание:**
    - Для обеспечения обмена данными в режиме реального времени между клиентами и сервером система Speculorg.Terminal использует WebSocket-соединения. Это позволяет отправлять и получать обновления без необходимости постоянных запросов к серверу.

- **Основные аспекты:**
    - Поддержка реального времени: WebSocket обеспечивает двунаправленное постоянное соединение между клиентом и сервером.
    - Маршрутизация сообщений: Сообщения маршрутизируются к соответствующим обработчикам на сервере, обеспечивая своевременную обработку.
    - Безопасность: Используются защищённые соединения (wss://), аутентификация осуществляется при установке соединения.

- **Установка и управление соединениями:**
    - Аутентификация: При установке WebSocket-соединения клиент должен предоставить действительный JWT-токен.
    - Подписка на каналы: Клиент отправляет сообщение с запросом на подписку на определённые каналы или темы.
    - Heartbeat и поддержание соединения: Для поддержания активности соединения используются механизмы heartbeat.

- **Обработка ошибок и переподключение:**
    - Обработка разрывов соединения: Клиентские приложения должны уметь обнаруживать разрывы соединения и автоматически переподключаться.
    - Сообщения об ошибках: В случае ошибок сервер отправляет соответствующие сообщения с описанием проблемы.

- **Преимущества использования WebSockets:**
    - Мгновенное обновление данных: Обеспечивает низкую задержку в передаче информации.
    - Снижение нагрузки на сервер: Отсутствие необходимости в постоянных запросах (polling) снижает нагрузку на сервер и сеть.
    - Улучшенный пользовательский опыт: Пользователи получают актуальную информацию без задержек, что особенно важно в торговых приложениях.

- **Примеры взаимодействия:**
    - Получение обновлений рыночных данных:
        - Адаптер устанавливает WebSocket-соединение с Внешним сервисом и подписывается на интересующие его Активы.
        - Внешний сервис отправляет обновления котировок и объёмов в режиме реального времени.
    - Статус ордеров и сделок:
        - После размещения ордера Адаптер может получать обновления о его статусе (исполнен, отменён, частично исполнен) через WebSocket.
    - Уведомления о событиях:
        - Сигналы из `Speculorg.Terminal.Analytics.Service` или `Speculorg.Terminal.RiskManagement.Service` могут быть мгновенно переданы другим Компонентам или процессам для оперативного реагирования.
